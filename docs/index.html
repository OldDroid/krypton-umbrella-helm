Overview

Überblick

Subcharts live as plain directories under charts/ and declare the library as a local dependency (file://../krypton-lib). When the umbrella renders, Helm loads every chart’s templates into one shared namespace, so the krypton-lib.* helpers resolve without vendoring.

Subcharts liegen als einfache Verzeichnisse unter charts/ und deklarieren das Library-Chart als lokale Abhängigkeit (file://../krypton-lib). Beim Rendern lädt Helm die Templates aller Charts in einen gemeinsamen Namensraum — die krypton-lib.*-Helper sind daher ohne Vendoring auflösbar.

Resource naming & lanes

Ressourcennamen & Lanes

Every resource is named <subchart>-<laneName>[-<instance>]. The component type is deliberately not part of the name — the Kubernetes kind already tells the Deployment from the Service called krypton-banking-release; it is still passed to every helper because it selects the sync wave and prune protection. Several resources of one kind get an instance suffix, normalised to a DNS-1123 label. The lane is also stamped as app.kubernetes.io/part-of; an optional global.partOfPrefix prepends the umbrella name to that label (krypton-umbrella-release) without touching the names. The names get their own optional global.namePrefix: empty by default, acme renders acme-krypton-banking-release (shared resources included). Switching the lane renames everything consistently.

Jede Ressource heißt <subchart>-<laneName>[-<instance>]. Der Komponententyp ist bewusst nicht Teil des Namens — der Kubernetes-Kind unterscheidet das Deployment ohnehin vom Service namens krypton-banking-release; er wird trotzdem jedem Helper übergeben, weil er Sync-Wave und Prune-Schutz auswählt. Mehrere Ressourcen einer Art erhalten einen Instance-Suffix, normalisiert auf ein DNS-1123-Label. Die Lane wird zusätzlich als app.kubernetes.io/part-of gesetzt; ein optionales global.partOfPrefix stellt diesem Label den Umbrella-Namen voran (krypton-umbrella-release), die Namen bleiben unberührt. Die Namen haben ihr eigenes optionales global.namePrefix: per Default leer, acme rendert acme-krypton-banking-release (geteilte Ressourcen eingeschlossen). Ein Lane-Wechsel benennt alles konsistent um.

helm template krypton krypton-umbrella --set global.laneName=test
Guard: an unset or empty global.laneName fails the render loudly — no lane-specific resource can ever be created without a lane in its name. Only resources explicitly marked shared (next card) drop it.Absicherung: ein fehlendes oder leeres global.laneName lässt das Rendern laut fehlschlagen — keine Lane-spezifische Ressource entsteht je ohne Lane im Namen. Nur explizit als shared markierte Ressourcen (nächste Karte) lassen sie weg.

Shared resources without the lane

Geteilte Ressourcen ohne Lane

ConfigMaps and Secrets that every lane deployment in a namespace consumes only have to exist once. They live in their own subchart, krypton-shared, whose templates pass shared: true to metadata: the name drops the lane segment (krypton-shared-<key>) and the app.kubernetes.io/part-of label is omitted. Exactly one ArgoCD Application per namespace may own them — ArgoCD flags a second owner as a shared resource, Helm refuses it — so ownership is the plain deploy switch krypton-shared.enabled. The application subcharts reference the objects with the same helper call plus chart: krypton-shared, so a reference can never drift from the rendered name. The same subchart carries the namespace-wide NetworkPolicy (named krypton-shared, podSelector: {}): every pod in the namespace accepts ingress only from its own namespace and from the OpenShift router, so a Route is the only way in from another namespace; egress stays open, and networkPolicy.extraRules admits further peers such as openshift-monitoring.

ConfigMaps und Secrets, die jedes Lane-Deployment in einem Namespace nutzt, müssen nur einmal existieren. Sie leben in einem eigenen Subchart, krypton-shared, dessen Templates shared: true an metadata übergeben: Der Name verliert das Lane-Segment (krypton-shared-<key>), das app.kubernetes.io/part-of-Label entfällt. Genau eine ArgoCD-Application pro Namespace darf sie besitzen — ArgoCD meldet einen zweiten Eigentümer als Shared Resource, Helm verweigert ihn —, die Eigentümerschaft ist deshalb der gewöhnliche Deploy-Schalter krypton-shared.enabled. Die Anwendungs-Subcharts referenzieren die Objekte mit demselben Helper-Aufruf plus chart: krypton-shared, eine Referenz kann so nie vom gerenderten Namen abdriften. Dasselbe Subchart trägt die namespace-weite NetworkPolicy (Name krypton-shared, podSelector: {}): Jeder Pod im Namespace akzeptiert Ingress nur aus dem eigenen Namespace und vom OpenShift-Router, aus einem anderen Namespace führt der Weg also nur über die Route; Egress bleibt offen, weitere Peers wie openshift-monitoring öffnet networkPolicy.extraRules.

helm template krypton krypton-umbrella
helm template krypton-shared krypton-umbrella -f values-shared-only.yaml
helm template krypton krypton-umbrella --set krypton-shared.enabled=true
Ownership: one Application per namespace enables krypton-shared — the owning lane, or a dedicated shared Application via values-shared-only.yaml (see ArgoCD); every other lane keeps the default. Service-scoped sharing still exists: krypton-banking's config.shared renders its own ConfigMap as krypton-banking, gated by config.create. The slim umbrella ships the same krypton-shared subchart (see slim variant).Eigentümerschaft: eine Application pro Namespace aktiviert krypton-shared — die Eigentümer-Lane oder eine eigene shared-Application über values-shared-only.yaml (siehe ArgoCD); jede andere Lane behält den Default. Service-bezogenes Teilen gibt es weiterhin: config.shared von krypton-banking rendert dessen ConfigMap als krypton-banking, geschaltet über config.create. Das schlanke Umbrella bringt dasselbe krypton-shared-Subchart mit (siehe schlanke Variante).

Labels & annotations merge

Labels- & Annotations-Merge

Chart-generated standard keys merge with the static global.labels / global.annotations; CI annotations from Jenkins slot in right after (next card); the ArgoCD keys are applied last so they can never be shadowed. One krypton-lib.metadata include produces the whole block. Annotations for exactly one resource go into that call: extra (a dict), annotation (one key=value string) or annotationsFrom (a dotted values path such as route.annotations, or routes.<name>.annotations per instance inside a range, so one Route of many gets its HAProxy timeout) — merged after the CI annotations, below the ArgoCD keys.

Chart-generierte Standard-Keys verschmelzen mit den statischen global.labels / global.annotations; CI-Annotations aus Jenkins reihen sich direkt danach ein (nächste Karte); die ArgoCD-Keys kommen zuletzt und können nie überdeckt werden. Ein einziges krypton-lib.metadata-Include erzeugt den ganzen Block. Annotations für genau eine Ressource wandern in diesen Aufruf: extra (ein Dict), annotation (ein key=value-String) oder annotationsFrom (ein Punkt-Pfad in die Values wie route.annotations, oder routes.<name>.annotations je Instanz in einem range, sodass von mehreren Routes genau eine ihr HAProxy-Timeout bekommt) — gemergt nach den CI-Annotations, unterhalb der ArgoCD-Keys.

Annotations for exactly one resource

Annotations für genau eine Ressource

global.annotations and <subchart>.annotations reach every resource. For a single one — the HAProxy timeout of one Route, not of the Deployment next to it — the metadata call takes three optional arguments: extra (a dict; the slim library calls it extraAnnotations), annotation (one key=value string, the one-liner form of the same thing) and annotationsFrom (a dotted path below .Values). The path form is what a template uses when the annotations belong in the values: it tolerates a missing path, so inside a range over several Routes only the instances that carry a routes.<name>.annotations block get one, and it fails the render when the path holds anything but a map. All three merge after the CI annotations and below the two ArgoCD keys.

global.annotations und <subchart>.annotations erreichen jede Ressource. Für eine einzelne — das HAProxy-Timeout einer Route, nicht des Deployments daneben — nimmt der metadata-Aufruf drei optionale Argumente: extra (ein Dict; das schlanke Library-Chart nennt es extraAnnotations), annotation (ein key=value-String, die Einzeiler-Form desselben) und annotationsFrom (ein Punkt-Pfad unterhalb von .Values). Die Pfad-Form nimmt ein Template, wenn die Annotations in die Values gehören: Sie toleriert einen fehlenden Pfad, in einem range über mehrere Routes bekommen also nur die Instanzen mit einem routes.<name>.annotations-Block eine, und sie lässt das Rendern fehlschlagen, wenn der Pfad etwas anderes als eine Map enthält. Alle drei werden nach den CI-Annotations und unterhalb der beiden ArgoCD-Keys gemergt.

helm template krypton krypton-umbrella --set krypton-banking.route.annotations.haproxy\.router\.openshift\.io/timeout=300s
One mechanism, three spellings: extra/extraAnnotations is the dict form, annotation writes one entry of that dict inline, annotationsFrom looks the dict up in the values with nil-safe navigation and stringified values. Combined in one call they merge in exactly that order. The slim umbrella’s krypton-payments Route passes .Values.route.annotations as extraAnnotations — equivalent to annotationsFrom "route.annotations" as long as the path always exists.Ein Mechanismus, drei Schreibweisen: extra/extraAnnotations ist die Dict-Form, annotation schreibt einen Eintrag dieses Dicts inline, annotationsFrom schlägt das Dict nil-sicher in den Values nach und stringifiziert die Werte. In einem Aufruf kombiniert mergen sie genau in dieser Reihenfolge. Die krypton-payments-Route des schlanken Umbrellas reicht .Values.route.annotations als extraAnnotations durch — gleichwertig zu annotationsFrom "route.annotations", solange der Pfad immer existiert.

Pod selectors: Deployment ↔ Service

Pod-Selektoren: Deployment ↔ Service

A Deployment's spec.selector, its pod template labels and the Service selector must agree, or the Service routes to nothing. krypton-lib.selectorLabels renders the identity all of them share: app.kubernetes.io/name (the subchart), app.kubernetes.io/instance (the Helm release, i.e. the ArgoCD Application) and app.kubernetes.io/part-of (the lane label, [<partOfPrefix>-]<laneName>). The pod template takes the full krypton-lib.labels set, which contains exactly these three values, so the selector always matches; the lane in the selector keeps a Service, PDB or NetworkPolicy of one lane from ever picking up another lane's pods in the same namespace.

Der spec.selector eines Deployments, seine Pod-Template-Labels und der Service-Selektor müssen übereinstimmen, sonst routet der Service ins Leere. krypton-lib.selectorLabels rendert die Identität, die alle drei teilen: app.kubernetes.io/name (das Subchart), app.kubernetes.io/instance (das Helm-Release, also die ArgoCD-Application) und app.kubernetes.io/part-of (das Lane-Label, [<partOfPrefix>-]<laneName>). Das Pod-Template bekommt den vollen krypton-lib.labels-Satz, der genau diese drei Werte enthält, der Selektor passt also immer; die Lane im Selektor verhindert, dass ein Service, PDB oder eine NetworkPolicy einer Lane je die Pods einer anderen Lane im selben Namespace einsammelt.

helm template krypton krypton-umbrella --set global.partOfPrefix=krypton-umbrella
One-way door: a Deployment selector is immutable. Renaming the lane creates a new Deployment anyway, but changing global.partOfPrefix on a lane that already runs changes only the selector and the apply is rejected — delete that lane's Deployments once, then sync again. Never add chart version or custom labels to the selector.Einbahnstraße: ein Deployment-Selektor ist unveränderlich. Eine Lane-Umbenennung erzeugt ohnehin ein neues Deployment, aber global.partOfPrefix auf einer bereits laufenden Lane zu ändern verändert nur den Selektor und der Apply wird abgelehnt — die Deployments dieser Lane einmalig löschen, dann erneut syncen. Nie Chart-Version oder eigene Labels in den Selektor aufnehmen.

CI annotations from Jenkins

CI-Annotations aus Jenkins

<subchart>.jenkins.annotations is merged into every resource of that subchart right after global.annotations — and only when the block exists, so a plain render carries no CI annotations. Jenkins sets it per sync through ArgoCD Helm parameters (dots inside a key are escaped as \.); scalar values are stringified, so a numeric build id is safe. Other subcharts are untouched.

<subchart>.jenkins.annotations wird direkt nach global.annotations in jede Ressource des Subcharts gemergt — und nur, wenn der Block existiert; ein normales Rendern trägt also keine CI-Annotations. Jenkins setzt ihn pro Sync über ArgoCD-Helm-Parameter (Punkte innerhalb eines Keys werden als \. escaped); skalare Werte werden stringifiziert, eine numerische Build-ID ist also sicher. Andere Subcharts bleiben unberührt.

helm template krypton krypton-umbrella --set krypton-banking.jenkins.annotations.jenkins\.io/build-number=1234 --set krypton-banking.jenkins.annotations.jenkins\.io/git-commit=abc1234
Merge order: standard → global.annotations → jenkins.annotations → per-call extra → ArgoCD sync-wave / sync-options. The ArgoCD keys always win. The slim library merges jenkins.annotations at the same position, after the subchart’s own annotations block.Merge-Reihenfolge: Standard → global.annotations → jenkins.annotations → extra pro Aufruf → ArgoCD Sync-Wave / Sync-Options. Die ArgoCD-Keys gewinnen immer. Die schlanke Library mergt jenkins.annotations an derselben Stelle, nach dem eigenen annotations-Block des Subcharts.

ConfigMap delivery & pod restarts

ConfigMap-Zustellung & Pod-Neustarts

config.data renders into the ConfigMap; the flags define delivery. envFrom consumers need the checksum roll — env vars never update in a running container. A service that watches its config file instead mounts it (mountPath; the kubelet refreshes the files, typically within a minute — whole-directory on purpose, subPath mounts would never refresh) and disables the roll.

config.data rendert in die ConfigMap; die Flags definieren die Zustellung. envFrom-Konsumenten brauchen den Checksum-Roll — Env-Variablen aktualisieren sich in laufenden Containern nie. Ein Service, der seine Config-Datei selbst überwacht, mountet sie stattdessen (mountPath; das Kubelet aktualisiert die Dateien, typischerweise binnen einer Minute — bewusst als ganzes Verzeichnis, subPath-Mounts würden nie aktualisieren) und deaktiviert den Roll.

helm template krypton krypton-umbrella --set krypton-banking.config.rollPodsOnChange=false --set krypton-banking.config.mountPath=/etc/krypton/config --set krypton-banking.config.envFrom=false

Sync waves: three-layer resolution

Sync-Waves: drei Auflösungsebenen

First hit wins: the subchart’s syncWaves.<component> (which already contains any umbrella override thanks to Helm coalescing), then global.syncWaves.<component>. Unconfigured components get no annotation.

Der erste Treffer gewinnt: syncWaves.<komponente> des Subcharts (enthält dank Helm-Coalescing bereits jedes Umbrella-Override), danach global.syncWaves.<komponente>. Unkonfigurierte Komponenten bekommen keine Annotation.

Cross-subchart ordering with syncWaveOffset

Subchart-übergreifende Reihenfolge mit syncWaveOffset

The offset is added to every resolved wave of the subchart, shifting its whole band behind (or before) its siblings while keeping the internal order. Components without a configured wave — implicitly wave 0 — are annotated with the bare offset, so they move with the block.

Der Offset wird auf jede aufgelöste Wave des Subcharts addiert und verschiebt das gesamte Band hinter (oder vor) seine Geschwister, bei unveränderter innerer Reihenfolge. Komponenten ohne konfigurierte Wave — implizit Wave 0 — erhalten den nackten Offset und wandern mit dem Block.

Implicit wave 0: with krypton-banking.syncWaveOffset=100, the HPA — which has no configured wave anywhere — renders sync-wave: "100" instead of escaping to wave 0. Convention: component waves stay within -9..9, offsets go in steps of 10, so bands never overlap.Implizite Wave 0: mit krypton-banking.syncWaveOffset=100 rendert der HPA — der nirgendwo eine Wave konfiguriert hat — sync-wave: "100", statt auf Wave 0 auszubrechen. Konvention: Komponenten-Waves bleiben in -9..9, Offsets in 10er-Schritten — Bänder überlappen nie.

Per-component prune protection

Prune-Schutz je Komponente

syncPrune.<component>: false (same resolution chain as the waves) stamps Prune=false: the resource survives app-level pruning even when its manifest disappears or the subchart is disabled. Setting a key to true re-enables pruning over a global false.

syncPrune.<komponente>: false (gleiche Auflösungskette wie die Waves) stempelt Prune=false: die Ressource überlebt das Pruning der App, selbst wenn ihr Manifest verschwindet oder das Subchart deaktiviert wird. Ein true reaktiviert das Pruning gegen ein globales false.

Deploy switches per subchart

Deploy-Schalter je Subchart

Every application subchart hangs on a condition flag in the umbrella Chart.yaml. Disabling removes all of its manifests from the release; ArgoCD prunes the live resources — except those protected via syncPrune.

Jedes Anwendungs-Subchart hängt an einem condition-Flag in der Umbrella-Chart.yaml. Deaktivieren entfernt alle seine Manifeste aus dem Release; ArgoCD pruned die Live-Ressourcen — außer den per syncPrune geschützten.

helm template krypton krypton-umbrella --set krypton-banking.enabled=false

Images & the per-lane registry switch

Images & der Registry-Schalter pro Lane

krypton-lib.image joins registry/repository:tag (a digest beats the tag). One umbrella key, global.imageRegistry, repoints every subchart at a proxy or air-gapped registry.

krypton-lib.image setzt registry/repository:tag zusammen (ein digest schlägt den Tag). Ein einziger Umbrella-Key, global.imageRegistry, biegt alle Subcharts auf eine Proxy- oder Air-Gapped-Registry um.

helm template krypton krypton-umbrella --set global.imageRegistry=proxy.bank.internal:5000

Multiple VaultStaticSecrets, lane-aware paths

Mehrere VaultStaticSecrets, Lane-abhängige Pfade

One VaultStaticSecret per entry under vault.secrets; the key becomes the instance suffix. Paths run through tpl, so the lane is templated in — release and test never read the same secrets. envFrom: true wires the materialised Secret into the Deployment.

Ein VaultStaticSecret je Eintrag unter vault.secrets; der Key wird zum Instance-Suffix. Pfade laufen durch tpl, die Lane wird also hineintemplatet — release und test lesen nie dieselben Secrets. envFrom: true verdrahtet das materialisierte Secret ins Deployment.

ServiceAccount: created or referenced

ServiceAccount: erzeugt oder referenziert

Each subchart runs under a dedicated SA at wave -2 — before the Vault objects that authenticate with it. Bind the VaultAuth Kubernetes role to exactly this name. create: false plus name: references an existing SA instead.

Jedes Subchart läuft unter einem eigenen SA in Wave -2 — vor den Vault-Objekten, die sich damit authentifizieren. Die VaultAuth-Kubernetes-Rolle an genau diesen Namen binden. create: false plus name: referenziert stattdessen einen bestehenden SA.

helm template krypton krypton-umbrella --set krypton-banking.serviceAccount.create=false --set krypton-banking.serviceAccount.name=legacy-vault-sa

Resources sized per lane

Resources pro Lane dimensioniert

Subcharts ship sensible defaults; the umbrella deep-merges lane sizing over them — the classic override on OpenShift with ResourceQuotas and LimitRanges.

Subcharts bringen sinnvolle Defaults mit; das Umbrella-Chart merged die Lane-Dimensionierung darüber — das klassische Override auf OpenShift mit ResourceQuotas und LimitRanges.

Optional components: PDB, HPA

Optionale Komponenten: PDB, HPA

Each follows the enabled-flag pattern and is steered per lane. While autoscaling.enabled is true, the Deployment stops rendering spec.replicas, so ArgoCD and the HPA never fight over the replica count. The namespace-wide NetworkPolicy is not a per-lane component — it is a shared resource of krypton-shared (see shared resources).

Jede folgt dem Enabled-Flag-Muster und wird pro Lane gesteuert. Solange autoscaling.enabled aktiv ist, rendert das Deployment kein spec.replicas mehr — ArgoCD und HPA streiten nie um die Replikazahl. Die namespace-weite NetworkPolicy ist keine Lane-Komponente — sie ist eine geteilte Ressource von krypton-shared (siehe geteilte Ressourcen).

Rebranding the label domain

Label-Domain umbenennen

The generated label/annotation keys take their prefix from global.labelDomain, so the scaffold is reusable for other platforms with one values key — the library needs no edits.

Die generierten Label-/Annotation-Keys beziehen ihr Präfix aus global.labelDomain — das Gerüst ist damit über einen einzigen Values-Key für andere Plattformen wiederverwendbar, ohne Änderung am Library-Chart.

helm template krypton krypton-umbrella --set global.labelDomain=acme.dev

Guardrails

Leitplanken

Misconfiguration never degrades silently. The component catalog in the library validates every component key at render time; the per-chart values.schema.json validates structure and value shapes against the coalesced values — a typo made in the umbrella block fails in the subchart’s schema.

Fehlkonfiguration degradiert nie still. Der Komponentenkatalog im Library-Chart validiert jeden Komponenten-Key beim Rendern; die values.schema.json je Chart validiert Struktur und Wertformen gegen die koaleszierten Values — ein Tippfehler im Umbrella-Block schlägt im Schema des Subcharts fehl.

helm template krypton krypton-umbrella --set krypton-banking.syncWaves.rout=9
helm template krypton krypton-umbrella --set krypton-banking.syncWaves.route=abc
helm template krypton krypton-umbrella --set krypton-banking.vault.secrets.app.pth=x
Deliberately tolerated: configuring a catalogued type that a subchart does not (yet) render is allowed and has no effect — waves and prune flags can be staged before the manifest exists.Bewusst toleriert: einen katalogisierten Typ zu konfigurieren, den ein Subchart (noch) nicht rendert, ist erlaubt und wirkungslos — Waves und Prune-Flags lassen sich vor dem Manifest anlegen.
VariantVariante

Slim variant

Schlanke Variante

krypton-umbrella-slim/ is a second, self-contained umbrella whose library krypton-lib-slim generates metadata only: unified names with an optional instance identifier for several ConfigMaps / Secrets / VaultStaticSecrets per subchart, merged labels and annotations (global → subchart → call site), ArgoCD sync waves with the offset mechanism, and generic ArgoCD sync options. Everything below metadata: is written by the subchart itself. Both variants share the component catalog and the naming scheme (<subchart>-<lane>[-<instance>], lane label app.kubernetes.io/part-of), so the names are identical. Written for the Helm 3 line ArgoCD runs.

krypton-umbrella-slim/ ist ein zweites, eigenständiges Umbrella, dessen Library krypton-lib-slim nur Metadata erzeugt: einheitliche Namen mit optionalem Instanz-Bezeichner für mehrere ConfigMaps / Secrets / VaultStaticSecrets je Subchart, zusammengeführte Labels und Annotations (global → Subchart → Aufrufstelle), ArgoCD-Sync-Waves samt Offset-Mechanik und generische ArgoCD-Sync-Options. Alles unterhalb von metadata: schreibt das Subchart selbst. Beide Varianten teilen sich den Komponentenkatalog und das Namensschema (<subchart>-<lane>[-<instance>], Lane-Label app.kubernetes.io/part-of), die Namen sind also identisch. Geschrieben für die Helm-3-Linie, die ArgoCD nutzt.

Shared resources and CI annotations work the same way here. The slim umbrella ships its own krypton-shared subchart (ConfigMaps, Secrets, VaultStaticSecrets rendered with "shared" true, owned by exactly one Application via krypton-shared.enabled); krypton-payments references them through sharedEnvFrom with the same helper plus chart. <subchart>.jenkins.annotations is merged right after the subchart’s own annotations block — only when it exists.

Geteilte Ressourcen und CI-Annotations funktionieren hier genauso. Das schlanke Umbrella bringt ein eigenes krypton-shared-Subchart mit (ConfigMaps, Secrets, VaultStaticSecrets mit "shared" true gerendert, Eigentümer ist genau eine Application über krypton-shared.enabled); krypton-payments referenziert sie über sharedEnvFrom mit demselben Helper plus chart. <subchart>.jenkins.annotations wird direkt nach dem eigenen annotations-Block des Subcharts gemergt — nur, wenn er existiert.

helm template krypton-shared krypton-umbrella-slim -f krypton-umbrella-slim/values-shared-only.yaml
helm template krypton krypton-umbrella-slim --set krypton-payments.jenkins.annotations.jenkins\.io/build-number=1234
Full reference: krypton-umbrella-slim/README.md. The slim umbrella is excluded from the full chart via .helmignore and deployed as its own ArgoCD Application (path: krypton-umbrella-slim).Vollständige Referenz: krypton-umbrella-slim/README.de.md. Das schlanke Umbrella ist per .helmignore aus dem vollen Chart ausgenommen und wird als eigene ArgoCD-Application deployt (path: krypton-umbrella-slim).

Point one Application per lane at the chart directory. Waves order resources within each sync; the lane is set via a values file or a Helm parameter. Lane Applications leave krypton-shared.enabled at its default (off) and merely reference the shared objects; one additional Application per namespace owns them through values-shared-only.yaml.

Pro Lane zeigt eine Application auf das Chart-Verzeichnis. Die Waves ordnen die Ressourcen innerhalb jedes Syncs; die Lane kommt aus einer Values-Datei oder einem Helm-Parameter. Lane-Applications lassen krypton-shared.enabled auf dem Default (aus) und referenzieren die geteilten Objekte nur; eine zusätzliche Application pro Namespace besitzt sie über values-shared-only.yaml.
